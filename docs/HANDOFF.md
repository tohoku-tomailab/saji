# 改修申し送り書：実験データ処理ツール群

この文書は、既存の実験データ処理ツール（Python製）を改修する AI エージェントへの申し送りです。
設計上の決定事項、目標とする構成、作業の進め方をまとめています。

---

## 0. この文書の読み方と作業の原則

- **最初に全文を読むこと。** 途中で実装を始めない。
- **既存実装はすでに一通り動いている。** この文書は、既存のコードを目標構成へ寄せるための指針であり、ゼロから作り直す指示ではない。既存の良い部分は活かす。
- **作業はまず「調査と差分報告」から始める**（§9 のフェーズ0）。報告して人間の承認を得るまでは、大きな構造変更をしない。
- ディレクトリ名、クラス名、関数名などの具体名は例として示している。既存コードに合理的な命名があれば、そちらを優先してよい。ただし §2 の「決定事項」は変えないこと。
- 判断に迷ったら §10 の優先順位に従う。それでも決められないときは、実装せずに人間へ質問する。
- **不可逆な操作はしない。** リポジトリの公開設定の変更、git 履歴の書き換え、force push、実データの削除などは、人間の明示的な指示がない限り行わない。

## 1. 背景と目的

研究室で使う実験データ処理（CSV やテキストの整形、集計、可視化、簡単な分析、PDF の操作など）を自動化したスクリプト群がある。改修の目的は次の3つ。

1. **研究室メンバーが使える Web ツールにする。** メンバーの多くは Python の授業経験はあるが、ターミナルや Web 開発には慣れていない。ブラウザで開くだけで使えることを目指す。
2. **AI エージェントが CLI から呼び出せるようにする。** 人間がエージェントに「このデータをざっくり処理して」と依頼できる状態にする。
3. **作成者がいなくなっても保守できるようにする。** 後任が AI エージェントと対話するだけで、修正や機能追加ができる状態にする。

## 2. 決定事項（変更しないこと）

### 2.1 確定した方針

| 項目 | 決定内容 |
|---|---|
| 実装言語 | **Python に統一する。** 処理ロジックは Python にだけ置く。 |
| 構成 | **共通のコアを1つ持ち、その上に CLI と Web を薄くかぶせる。** |
| Web の実行方式 | **Pyodide（ブラウザ内 Python）を直接使う。** サーバは持たない。静的ホスティング（GitHub Pages を想定）で配信する。 |
| Web の UI | **素の HTML / CSS / JS で作る。** UI フレームワーク（Streamlit など）は使わない。 |
| ツール定義 | **Python 側の1か所で定義し、CLI の引数、Web のフォーム、ドキュメントをそこから生成する**（§3.2）。 |
| グラフ | **何を描くかは Python が決め、Plotly の図の形式（JSON）で返す。** ブラウザでは Plotly.js でプレビューを描き、成果物の図は同じ JSON から matplotlib で生成する（§3.6）。 |
| Web のビルド | **npm やバンドラは使わない。** ビルドは Python のスクリプト1本で行う（§3.5）。 |
| 重い処理 | Pyodide で動かせないものや重いものは **CLI 専用** とする（判定基準は §3.5）。 |
| データの扱い | 実験データはリポジトリに含めない。Web でもデータは利用者のブラウザ内だけで処理し、外部へ送信しない。 |
| 公開 | GitHub で Public リポジトリにすることを前提に準備する。実際に公開するかどうかは人間が判断する（§8）。 |

### 2.2 却下した案と理由

将来「こうしたほうがよいのでは」と考えたときは、まずこの表を確認すること。

| 却下した案 | 理由 |
|---|---|
| Streamlit / Gradio などの UI フレームワーク | デザインの柔軟性が低い。HTML / CSS は AI に書かせたほうが自由度が高く、手間も小さい。 |
| サーバで動かす Web アプリ（FastAPI など） | サーバの維持管理が作成者の卒業後に途絶えるリスクが高い。実験データ（未発表のものを含む）をサーバへアップロードさせたくない。 |
| Web 用に処理を JavaScript で再実装する | 同じ処理が二言語に分かれ、片方だけ更新される事故が起きる。後任の多くは JS を書けない。 |
| CLI だけを配布する | ターミナルに不慣れなメンバーが使えない。 |
| エージェント向けに MCP サーバを用意する | 現時点では不要。設計のよい CLI があればエージェントは十分に使える。必要になったら CLI の上に薄く追加する。 |
| ツールごとに個別の HTML ページを作る | ツールが増えるたびに JS の保守が増え、Python しか書けない後任が手を出せなくなる。汎用の外枠と、例外用の専用パネルで対応する。 |
| グラフの描画処理を手法ごとに JS で書く | 手法固有の知識（軸の向き、参照ピーク、バックグラウンドなど）が JS に散らばる。手法の知識は Python に置き、JS は汎用の描画だけを担う。 |
| CLAUDE.md を置く | Claude Code 2.1.277 以降は、CLAUDE.md がなければ AGENTS.md を読む。CLAUDE.md を置くと AGENTS.md が読まれなくなるため、置かない。 |

### 3.2 ツール定義（唯一の情報源）

各ツールは、宣言的な `TOOL` 定義と、純粋な処理関数 `run()` の組で表す。CLI の引数、Web のフォーム、`--help`、ドキュメントの一覧は、すべてこの定義から生成する。**同じ情報を二か所以上に手で書かないこと。**

```python
# src/<package>/tools/normalize.py
TOOL = Tool(
    name="normalize",
    summary="装置Xの出力をベースライン補正して正規化する",
    description="詳細な説明。前提となる入力形式は docs/data-formats.md の『装置X』を参照。",
    inputs=[FileInput("raw", accept=[".csv"], multiple=True)],
    params=[
        Param("baseline_min", type=float, default=0.0, unit="nm", help="ベースライン区間の下限"),
        Param("baseline_max", type=float, default=10.0, unit="nm", help="ベースライン区間の上限"),
    ],
    web=True,               # False なら CLI 専用
    packages=["numpy"],     # Pyodide で読み込む追加パッケージ
)

def run(inputs: dict[str, list[InputFile]], params: dict) -> Result:
    ...
```

- `InputFile` は「ファイル名」と「内容（bytes）」を持つ。
- `Result` は「出力ファイル（相対パスと bytes の組）のリスト」「ログ」「警告」「プレビュー用の図（§3.6 の図の JSON のリスト。任意）」を持つ。
- パラメータの型は、JSON で表現できる単純なもの（int / float / str / bool / 選択肢）に限る。複雑な型が必要になったら、先に人間に相談する。

### 3.3 コアの規約

- **`run()` はファイルシステムに触れない。** 入力は bytes で受け取り、出力も bytes で返す。パスの解決、フォルダの作成、書き込みは CLI 層と Web 層の役目。
- **`run()` は画面について何も知らない。** print、input、表示処理を入れない。情報を伝えたいときは Result のログや警告に入れる。
- **決定的にする。** 同じ入力と同じパラメータからは同じ出力が出るようにする。乱数を使う場合は seed をパラメータにする。
- **ネットワークに接続しない。**
- **依存を追加するときは、Pyodide で動くことを確認する**（`web=False` のツールだけが使う依存は除く）。依存を追加したら、その理由を docs に記録する。

### 3.4 CLI（人間とエージェント向け）

- 形式は `<command> <tool> [inputs...] [--param value ...]`。
- **完全に非対話にする。** 確認プロンプトを出さない。上書きなどは `--force` で制御する。
- **`--help` を充実させる。** エージェントはまずこれを読む。各パラメータに単位、既定値、説明を表示する。`<command> list` でツール一覧を出す。
- **`--json`**：標準出力に結果の要約を JSON で出す（出力フォルダのパス、処理件数、警告など）。人間向けのメッセージは標準エラー出力に出す。
- **`--dry-run`**：実際には書き込まず、何をするかだけを表示する。
- **`--output-dir`**：出力先の親フォルダを変更できるようにする（既定は `outputs/`）。
- **終了コード**：0 は成功、1 は処理中のエラー、2 は引数や入力の誤り。
- 配布は `uv tool install git+<リポジトリURL>` で入れられる形にする。

### 3.5 Web（Pyodide）

- **外枠は1つだけ作る。** ファイル選択、パラメータフォーム、実行、プレビュー、ダウンロードを汎用的に行う。**原則として、ツールを追加するときに JS を書く必要がない状態を保つ。**
- **ビルドと実行の流れ。**
  - ビルド時（`scripts/build_web.py`）：Python パッケージを wheel にする。全ツールの TOOL 定義を `tools.json` に、バージョンと git のコミットを `version.json` に書き出す。**npm やバンドラは使わない。**
  - 実行時：`index.html` が `tools.json` を読み、ツール一覧とフォームを即座に表示する（Pyodide の読み込みを待たない）。並行して Worker が Pyodide と wheel を読み込む。実行すると Python が Result を返し、JS がプレビューの描画と zip の作成を行う。
- **フォームは `tools.json` から自動で生成する。** 対応するパラメータの型は §3.2 に挙げたものに限る。
- **専用パネル（例外）。** 汎用フォームで表現できない操作（例：グラフ上をドラッグしてバックグラウンドの範囲を決める）が必要なツールに限り、`web/panels/<tool>.js` を置いてよい。外枠は、このファイルがあれば読み込んで、汎用フォームの代わりに使う。専用パネルを作るときは、その理由を `docs/decisions/` に記録する。専用パネルでも、処理そのものは Python の `run()` で行う。
- **Pyodide は Web Worker で動かす。** Pyodide 314 系では classic worker が使えないため、module worker（`type: "module"`）を使う。UI スレッドで Python を実行しない。
- **ページを開いた直後から、Worker で Pyodide を読み込み始める。** 利用者がファイルを選んでいるあいだに読み込みを終わらせ、体感の待ち時間を減らす。読み込みの状態は画面に表示する。
- **パッケージは必要な分だけ読み込む。** そのツールの `packages` を、ツールを選んだときに `loadPackage` する。
- **Pyodide のバージョンは固定する。** CDN を使う場合もバージョンを明示する。最新版を自動で追う書き方はしない。
- **フォルダ単位の入力に対応する。** `<input type="file" webkitdirectory>` を使う。ドラッグ＆ドロップにも対応する。
- **出力は zip でダウンロードする。** ファイル名は `YYYYMMDD_hhmmss-{tool}.zip` とし、中身は CLI の出力フォルダと同じ構成にする（§4）。
- **外部へ一切送信しない。** 解析用のタグ（アクセス解析など）も入れない。このことを画面にも明記する（「データはこのブラウザの外に送信されません」）。
- Python 側のコアは、ビルド時に wheel か zip にまとめて Worker から読み込む。ソースを二重管理しない。

**`web=False`（CLI 専用）にする判断基準**。どれか1つに当てはまれば CLI 専用とする。

- 外部バイナリ（Ghostscript、OCR エンジンなど）や subprocess が必要。
- threading / multiprocessing が必要。
- Pyodide で動かない依存がある。
- 想定する入力が1回あたり数百MBを超える。ブラウザのメモリは実用上およそ2GBが限界で、pandas は読み込むと元のファイルの数倍に膨らむ。
- Pyodide 上での実行時間が、利用者の待てる範囲（目安は数十秒）を大きく超える。

CLI 専用のツールも Web の一覧には表示する。そのうえで「CLI 専用」と示し、CLI での実行方法を案内する。

### 3.6 グラフ

**方針：「何を描くか」は Python が決め、「どう描くか」は汎用の描画器が担う。**

- **図の形式は Plotly の図の JSON（`data` と `layout`）とする。** Python は、`plotly` パッケージを使わずに dict として組み立てる（Web で読み込むパッケージを減らすため）。組み立てを補助する関数は `core/plot/` に置く。
- **使ってよい要素を限定する。** 線と散布図（`scatter`）、軸の設定（ラベル、単位、範囲、逆向き、対数）、凡例、注釈、縦線と網掛けの範囲（`shapes`）、複数系列のずらし（オフセット）。これ以外の要素が必要になったら、先に人間に相談する。許可した要素の一覧は `docs/design.md` に記載する。
- **描画器は2つ。どちらも手法の知識を持たない。**
  - ブラウザのプレビュー：`web/plot.js` が Plotly.js で描く（`Plotly.newPlot` にそのまま渡す）。
  - 成果物の図：`core/plot/` の変換器が、同じ JSON を matplotlib で SVG / PDF にする。許可した要素だけに対応すればよい。
  - プレビューと成果物の見た目が完全に一致する必要はない。軸、データ、注釈の内容が一致していればよい。
- **手法固有の知識は `techniques/` に置く。** 例えば次のようなもの。
  - XPS：結合エネルギー軸を逆向きにする、バックグラウンド（Shirley など）とピーク成分を重ねる、帰属の注釈をつける。
  - XRD：2θ 軸を使う、参照カードのピークをスティックで描く、複数のパターンをずらして並べる、強度を対数にする選択肢を持つ。
  - 共通部分（軸ラベルと単位の書式、オフセット、配色、フォントなど）は `core/plot/` に置き、手法ごとのモジュールがそれを使う。
- **グラフの作成もツールにする。** 例：`xrd-plot`、`xps-plot`。出力は、成果物の図（SVG / PDF）、図の元データとなる整形済みの CSV（他のソフトで仕上げるため）、図の JSON（再描画のため）の3つとする。
- 処理系のツール（補正や正規化など）も、確認用のプレビューの図を Result に含めてよい。

## 4. 出力規約

- CLI の出力先は `outputs/YYYYMMDD_hhmmss-{tool}/`。時刻はローカル時刻（JST）を使う。
- 同じ秒にフォルダ名が衝突した場合は、末尾に `-2`、`-3` … を付ける。
- `outputs/` は `.gitignore` に入れる。
- 各出力フォルダには必ず `manifest.json` を置く。

```json
{
  "tool": "normalize",
  "tool_version": "0.3.1",
  "git_commit": "a1b2c3d",
  "runtime": "cli",
  "python_version": "3.14.2",
  "pyodide_version": null,
  "started_at": "2026-09-24T14:03:12+09:00",
  "finished_at": "2026-09-24T14:03:15+09:00",
  "params": { "baseline_min": 0.0, "baseline_max": 10.0 },
  "inputs": [ { "name": "sample01.csv", "size": 20480, "sha256": "..." } ],
  "outputs": [ "sample01_normalized.csv" ],
  "warnings": []
}
```

- Web で実行した場合は `runtime: "web"` とし、`pyodide_version` を記録する。`git_commit` はビルド時に埋め込む。
- 入力ファイルはフルパスで記録しない。ファイル名だけを記録する（ユーザー名などの流出を防ぐため）。

## 5. 再現性とバージョン

- ツールのバージョンはパッケージのバージョンで管理する。出力が変わる変更をしたら、バージョンを上げる。
- **CLI 側の Python と Pyodide の Python のバージョンを揃える**（Pyodide 314.x は Python 3.14 に対応）。揃えられない事情があれば報告する。
- Pyodide のメジャー更新は、Python の更新に合わせて年1回ある。更新の手順は `docs/maintenance.md` に書く。

## 6. テスト

- `tests/fixtures/` には **合成データだけ** を置く。実データ、および実データを加工したものは置かない。
- ツールごとにゴールデンテストを用意する（入力と期待される出力の組）。
- テストは次の2つの環境で通す。
  - ネイティブの Python（pytest）。
  - Pyodide（`pytest-pyodide` などを使う）。`web=True` のツールだけが対象。
- GitHub Actions で、push ごとに上記2つを実行する。
- CLI の `--json` 出力の形式と終了コードもテストする。
- 図の JSON はスナップショットテストの対象にする。matplotlib への変換は、許可した要素ごとにエラーなく描けることをテストする。

### 7.1 AGENTS.md（エージェント向けの目次）

**CLAUDE.md は作らない。** Claude Code 2.1.277 以降は、CLAUDE.md がないフォルダでは AGENTS.md を読む。CLAUDE.md（および CLAUDE.local.md）を置くと、そちらが優先されて AGENTS.md が読まれなくなる。README に「Claude Code は 2.1.277 以降を使うこと」と書いておく。

1. このリポジトリが何か（2〜3行）と、対象外のこと。

4. **却下した案**：§2.2 の要約。
5. **禁止事項**：実データをコミットしない、`run()` に I/O を入れない、外部へ送信しない、ツール定義の情報を二重に書かない、不可逆な git 操作をしない。
6. **ツール追加の手順**：`docs/adding-a-tool.md` へのリンクと、そのチェックリストの要約。
7. **テストの実行方法**：コマンドをそのまま書く。
8. **判断に迷ったとき**：§10 の優先順位。

### 7.2 docs/

- `design.md`：この申し送り書の §2〜§6 を、恒久的な設計文書として書き直したもの。
- `plotting.md`：図の JSON で許可している要素、共通の書式、手法ごとの描き方の約束。
- `data-formats.md`：装置やデータの種類ごとの入力フォーマット、列名、単位、既知の癖（例：「装置Yは先頭3行がメタデータ」）。**研究室固有の知識なので、コードから読み取れる内容はすべて書き出す。** 不明な点は「要確認」と明記して人間に質問する。
- `adding-a-tool.md`：TOOL 定義を書く → `run()` を実装する → 合成データとゴールデンテストを作る → 2つの環境でテストを通す → 必要ならデータ形式辞書を更新する、という手順をチェックリストで書く。
- `maintenance.md`：Pyodide と Python の年次更新、依存の更新、GitHub Pages へのデプロイの手順。
- `decisions/`：設計判断を1件1ファイルで記録する（日付、背景、決定、却下した案）。この申し送り書で決まった内容を最初の記録として登録する。

### 7.3 README.md（人間向け）

- Web 版の URL と使い方（スクリーンショットがあるとよい）。
- CLI のインストール方法と基本的な使い方。
- 「データは外部に送信されない」ことの説明。
- サポートはしない旨とライセンス。

## 8. 公開に向けた準備

リポジトリは Public での公開を前提に整える。**ただし、公開設定の変更は人間が行う。エージェントは行わない。**

- **実データの混入を調べる。** 現在のファイルだけでなく、git の履歴全体を対象にする。見つかったら削除せずに一覧にして報告する。履歴の書き換えは人間が判断する。
- **機微な情報を調べる。** コード、コメント、ファイル名、コミットメッセージに含まれる化合物名、試料名、共同研究先、個人名、装置のシリアル番号、ローカルの絶対パスなどを探す。候補を一覧にして報告する。削除するかどうかは人間が判断する。
- **pre-commit フックを入れる。** `outputs/` やデータ用フォルダの中身、および一定サイズを超えるファイルのコミットを拒否する。
- **LICENSE を用意する。** 種類は人間が決める（候補は MIT）。
- **`.gitignore` を整える。** `outputs/`、一時ファイル、仮想環境などを対象にする。

## 9. 作業の進め方

各フェーズの終わりに、実施内容と残った課題を報告する。**フェーズ0が終わったら、必ず止まって人間の承認を得ること。**

### フェーズ0：調査と差分報告（コードは変更しない）

- 既存のツールをすべて列挙する。ツールごとに、入出力、依存、処理の概要、Pyodide で動かせるかの見込み（§3.5 の基準による）を表にまとめる。
- 既存の構成とこの文書の目標構成との差分を整理する。
- 移行計画を立てる。どの順でどのツールを移すか、既存の使い方との互換性をどう扱うか。
- 既存の命名や構造のうち、活かすものと変えるものを示す。
- この文書と既存実装が矛盾する点、この文書だけでは決められない点を挙げる。
- **報告して承認を待つ。**

### フェーズ1：コアの基盤とパイロット

- `Tool`、`Param`、`FileInput`、`InputFile`、`Result`、manifest の生成など、コアの基盤を実装する。
- **最もよく使われるツールを1つだけ** 新しい構成に移し、CLI と Web の両方で動かして型を確立する。
- あわせて、グラフの仕組み（§3.6）も最小限で通す。図の JSON を返し、Plotly.js でプレビューを描き、matplotlib で SVG を出すところまで。
- パイロットの結果を報告し、基盤の設計を見直す点があれば提案する。

### フェーズ2：CLI の整備

- TOOL 定義から CLI を生成する。§3.4 の仕様（`--help`、`--json`、`--dry-run`、終了コード、`list`）をすべて満たす。
- `uv tool install` でインストールできることを確認する。

### フェーズ3：出力規約とテスト

- §4 の出力規約と manifest を実装する。
- 合成データ、ゴールデンテスト、2つの環境でのテスト、GitHub Actions を整える。

### フェーズ4：残りのツールの移行

- フェーズ0の計画に従い、残りのツールを1つずつ移す。1ツールごとにテストを通し、コミットを分ける。
- CLI 専用にするツールは、その理由を `docs/decisions/` に記録する。

### フェーズ5：Web の外枠の仕上げ

- §3.5 の仕様をすべて満たす（`build_web.py`、`tools.json` からのフォーム生成、専用パネルの読み込みの仕組みを含む）。
- 見た目を整える。落ち着いた、読みやすいデザインにする。ライトテーマとダークテーマの両方に対応し、スマートフォン幅でも崩れないようにする。
- GitHub Pages へのデプロイ手順を用意する。

### フェーズ6：ドキュメント

- §7 のドキュメントをすべて作る。
- 最後に、**AGENTS.md だけを読んだ新しいエージェントが、ツールを1つ追加できるか** を想定して見直す。

### フェーズ7：公開準備のチェック

- §8 の調査を実施し、報告する。

## 10. 判断に迷ったときの優先順位

1. **実験データを守る。** 外部に送信しない、リポジトリに入れない。
2. **処理結果の正しさと再現性を保つ。** 既存の処理と結果が変わる場合は、必ず報告する。
3. **後任が保守できること。** Python だけで完結する、仕組みが単純である、ドキュメントがある。
4. **研究室メンバーにとっての使いやすさ。**
5. **性能と見た目。**

既存ツールの出力を変える変更（数値の丸め方、列の順番、ファイル名など）は、それが改善であっても **勝手に行わず、報告して判断を仰ぐ**。

## 11. 人間に確認が必要な事項

以下は未決定である。該当する場面になったら質問すること。

- 既存の CLI や使い方との互換性をどこまで保つか（フェーズ0の報告後に決める）。
- 各ツールで想定する入力サイズ（CLI 専用にするかどうかの判断に使う）。
- ライセンスの種類。
- Public で公開するかどうかと、その時期（指導教員の了承、所属機関の知財ポリシー、共同研究契約の確認が前提）。
- リポジトリを置く場所。**研究室の GitHub Organization に置くことを推奨する**（個人アカウントに置くと、作成者の卒業後に管理できなくなるため）。
- データ形式辞書のうち、コードから読み取れない点。
- 論文用の図を最終的にどこで仕上げるか（matplotlib の出力をそのまま使うのか、Origin などで仕上げるのか）。後者なら、成果物の重点を「そのソフトに読み込みやすい CSV」に置き、matplotlib の図は確認用の簡素なものでよい。
- 専用パネルが必要になりそうなツールの有無（フェーズ0で候補を挙げる）。
